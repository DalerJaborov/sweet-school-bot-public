# Shirin Sweets — Android-приложение

Нативная Android-обёртка: полноэкранный `WebView` поверх
`https://shirinsweets.online/course`. Существует ради одной вещи, которую
нельзя сделать из браузера/PWA — `FLAG_SECURE` (см. `MainActivity.kt`),
системный флаг окна, который блокирует скриншоты и запись экрана, пока
приложение открыто (тот же механизм, которым Telegram помечает "защищённый
контент"). Курс платный, поэтому это дополнительный защищённый вход для
Android — iPhone как и раньше пользуются Safari/PWA, сайт этим не заменяется.

Распространяется ДВУМЯ путями одновременно:
- **.apk для прямого скачивания** с сайта
  (`https://shirinsweets.online/app/shirin-sweets.apk`) — работает уже
  сейчас, ставится вручную, Android покажет предупреждение "из неизвестного
  источника" (это нормально для прямых .apk, не баг).
- **.aab для Google Play Console** — владелец создаёт объявление в Play
  Console и загружает `android-app/dist/shirin-sweets.aab` вручную (см. ниже
  "Что нужно сделать владельцу"). После публикации в Play Store автообновления
  и без предупреждений при установке.

Оба файла собираются одним и тем же workflow из одного и того же кода —
разница только в способе распространения, не в самом приложении.

## Как пересобрать

Сборка идёт в облаке (GitHub Actions), ничего локально ставить не нужно:

1. Запушить изменения в `android-app/**` в `main` — workflow
   `.github/workflows/android-apk.yml` соберёт .apk и .aab автоматически, либо
2. Открыть вкладку **Actions → Android APK → Run workflow** на GitHub
   (или `gh workflow run android-apk.yml`) для сборки без изменений в коде.

Готовые файлы — artifacts запуска workflow: "shirin-sweets-apk" и
"shirin-sweets-aab" (`gh run download <run-id> -n shirin-sweets-apk -n
shirin-sweets-aab`).
- .apk → положить в `apps/web/public/app/shirin-sweets.apk` и задеплоить
  `apps/web` как обычно (владелец — по ssh, как для остальных изменений сайта).
- .aab → загрузить в Play Console вручную (см. ниже), на сайт не выкладывается.

### Локально (Android Studio)

Нужен только Android Studio (Giraffe/Koala и новее) — JDK 17 и Android SDK
уже поставляются вместе с ним:

1. Открыть папку `android-app/` как проект.
2. Studio сама скачает Gradle 8.7 по `gradle-wrapper.properties` и нужные
   компоненты SDK (compileSdk/targetSdk 34, minSdk 24) при первой синхронизации.
3. `./gradlew assembleRelease` — локально боевого upload-keystore нет (он не
   в репозитории, см. "Подпись" ниже), поэтому release тихо подписывается
   debug-ключом. Этого достаточно, чтобы собрать и проверить приложение на
   своём телефоне; настоящий подписанный .aab для Play Console выходит
   только из CI, где есть секреты.

## Как поднять версию

В `app/build.gradle.kts`:
```kotlin
versionCode = 2          // +1 на каждый релиз, только вверх
versionName = "1.0.1"    // человекочитаемая версия
```
Без роста `versionCode` ни прямой .apk не встанет поверх старой версии на
телефоне, ни Play Console не примет новую загрузку.

## Что внутри

- `MainActivity.kt` — вся логика в одном экране:
  - `FLAG_SECURE` — защита от скриншотов/записи экрана (см. выше).
  - `WebView` с включёнными JS, `domStorageEnabled` (нужно сайту — сессия и
    прогресс курса лежат в localStorage/IndexedDB) и сторонними куками.
  - `ServiceWorkerControllerCompat` (androidx.webkit) — офлайн-уроки сайта
    (`apps/web/public/course-sw.js`, Cache Storage + IndexedDB) работают в
    WebView так же, как в мобильном браузере — см. "Офлайн" ниже.
  - Кнопка "назад" системы Android — сначала назад по истории WebView, потом
    выход из приложения.
  - Ссылки не на `shirinsweets.online` (WhatsApp/Telegram/`tel:` из блока
    контактов на сайте) открываются во внешнем приложении, а не в WebView.
  - `onShowFileChooser` — без него `<input type="file">` в чате (загрузка
    фото чека) в WebView молча ничего не делает; тут — системный
    файл/камера-пикер.
  - Android App Links (`onNewIntent`/`urlToLoad`) — ссылка на курс из
    Instagram-директ/WhatsApp открывается прямо в приложении, если оно
    установлено и домен подтверждён (см. "Android App Links" ниже).
- `BuildConfig.COURSE_URL` — адрес курса, задан в `app/build.gradle.kts`,
  чтобы поменять его (например, на стейджинг) без правки кода.
- Иконка — `apps/web/public/icons/icon-512.png` как foreground адаптивной
  иконки на сплошном малиновом фоне (`#C9376B`, бренд-цвет сайта); PNG для
  всех плотностей уже сгенерированы и лежат в `res/mipmap-*`.
- Заставка — на Android 12+ (API 31) настоящий системный Splash Screen API
  (`res/values-v31/themes.xml`, без библиотек), на более старых версиях —
  простой фон темы активности того же малинового цвета с логотипом
  (`res/drawable/splash_background.xml`).
- Сборка НЕ минифицирована (`isMinifyEnabled = false`) — обёртка маленькая,
  ужимать нечего, а R8 добавляет риск сломать WebView-колбэки без пользы.

## Офлайн-уроки в приложении

Сайт умеет кешировать оболочку курса и скачанные уроки через
`/course-sw.js` (Service Worker) + Cache Storage/IndexedDB — ученица
открывает уже скачанный урок без сети. Голый `android.webkit.WebView` не
даёт этого «из коробки» так же надёжно, как настоящий браузер: мы явно
проверяем `WebViewFeature.SERVICE_WORKER_BASIC_USAGE` и подключаем
`ServiceWorkerClientCompat` (`androidx.webkit:webkit`), чтобы Service Worker
точно был разрешён и вёл себя как в мобильном Chrome/Safari, а не тихо
бездействовал на части устройств. Прямого управления запросами внутри SW мы
не делаем (`shouldInterceptRequest` возвращает `null` — «пропусти как
обычно»), это не подмена сети, а гарантия, что она вообще подключена.

## Android App Links

Ссылка вида `https://shirinsweets.online/course`, `/course/...` или короткая
`/l/<код>` (из чата, Instagram-директ, WhatsApp) должна открываться прямо в
приложении, если оно установлено — это `<intent-filter
android:autoVerify="true">` в `AndroidManifest.xml`. Android проверяет право
приложения на такие ссылки через
`apps/web/public/.well-known/assetlinks.json` — файл на сервере,
подтверждающий, что этот пакет (`online.shirinsweets.course`) и этот домен
принадлежат одному владельцу.

**Важно про фингерпринт в assetlinks.json.** Сейчас там прописан SHA-256
сертификата upload-keystore (см. "Подпись" ниже) — это тот ключ, которым CI
подписывает .aab перед загрузкой в Play Console. Но если при первой загрузке
в Play Console включить **Play App Signing** (это включено по умолчанию и
Google явно это рекомендует), Google **перевыпускает** приложение под
собственным ключом для реальной раздачи пользователям — и именно ЕГО
отпечаток нужен в assetlinks.json, а не отпечаток upload-ключа. Отпечаток
upload-ключа ниже — временный, пока не выполнены шаги 4–5 из следующего
раздела.

Если ссылка не открывается в приложении, а падает в браузер — это не
поломка, это ожидаемое поведение до тех пор, пока фингерпринт не обновлён
на настоящий, и/или пока Google не завершил проверку домена (может занять
до суток после первой публикации).

## Подпись (upload-keystore для Play Store)

`android-app/.secrets/upload-keystore.jks` — боевой ключ, которым подписан
.aab для Play Console. Он **НЕ в git** (см. `.gitignore`) — CI получает его
через зашифрованные секреты GitHub Actions:

| Секрет | Что внутри |
|---|---|
| `ANDROID_KEYSTORE_BASE64` | сам `.jks`-файл, в base64 |
| `ANDROID_KEYSTORE_PASSWORD` | пароль хранилища |
| `ANDROID_KEY_ALIAS` | `shirinsweets` |
| `ANDROID_KEY_PASSWORD` | пароль ключа (у PKCS12-хранилищ = паролю хранилища) |

Сами файл и пароли лежат локально в `android-app/.secrets/` (см.
`README-KEYSTORE.txt` в этой папке — там же объяснение, почему потеря этого
ключа означает невозможность выпустить обновление приложения под тем же
пакетом, если Play App Signing не включён). **Владельцу нужно скопировать
`android-app/.secrets/upload-keystore.jks` и пароли из `.env` в надёжное
место (менеджер паролей + отдельный бэкап файла) — это единственная читаемая
копия, GitHub-секреты нельзя прочитать обратно даже нам.**

Локальные сборки (Android Studio) этих секретов не видят и автоматически
подписываются debug-ключом — этого достаточно для проверки на своём
телефоне, но такой .apk/.aab нельзя грузить в Play Console.

## Что нужно сделать владельцу в Play Console (мы это сделать не можем)

У владельца уже есть аккаунт разработчика Google Play. Дальше — вручную,
через сайт Play Console (`play.google.com/console`):

1. **Создать приложение**: название "Shirin Sweets", пакет
   `online.shirinsweets.course`, категория — Образование/Еда и напитки.
2. **Загрузить `android-app/dist/shirin-sweets.aab`** (скачать из последнего
   успешного запуска workflow "Android APK", artifact "shirin-sweets-aab")
   в раздел Production (или сначала Internal testing — рекомендуется для
   первого релиза).
3. Убедиться, что включён **Play App Signing** (в разделе Setup → App
   integrity) — обычно включается автоматически при первой загрузке через
   Play Console UI, ничего специально настраивать не нужно, просто не
   отключать.
4. После первой успешной загрузки — зайти в **Setup → App integrity** и
   скопировать оттуда **"App signing key certificate" → SHA-256** (это
   ключ, которым Google реально подписывает приложение для пользователей,
   он отличается от нашего upload-ключа).
5. Прислать этот SHA-256 обратно — им нужно заменить фингерпринт в
   `apps/web/public/.well-known/assetlinks.json`, иначе Android App Links
   (открытие ссылок из Instagram/WhatsApp прямо в приложении) не заработает.
6. Заполнить обязательные разделы Play Console: Store listing (описание,
   скриншоты, значок — есть отдельная работа по контенту и странице
   политики конфиденциальности), Content rating questionnaire, Data safety
   form (какие данные собирает приложение — по сути те же данные, что и
   сайт: логин ученицы, прогресс курса; камеру/микрофон/контакты не
   запрашивает вовсе). Без этого Google не пропустит релиз даже с готовым
   .aab.
7. Отправить на модерацию — обычно 1–3 дня на первую публикацию, быстрее на
   последующие обновления.

Прямой .apk на сайте можно оставить и после публикации в Play Store — как
запасной канал для тех, кто не хочет ставить приложение через Play (или в
регионах с ограниченным доступом к Play Store).
